# giga-transcribe

Локальная офлайн-транскрипция встреч в markdown для **русского** аудио/видео на базе
[GigaAM](https://github.com/salute-developers/GigaAM) (ASR) и
[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) (диаризация спикеров).

Наводишь на любую запись - получаешь markdown-стенограмму с таймкодами и разметкой по спикерам. Без
облака, без API-ключей, без утечки данных с машины. Идет как CLI плюс macOS Быстрое действие Finder.

```
transcribe-meeting "встреча.mp4" --speakers 3   ->   встреча.md
```

## Почему не просто Whisper?

Для русского специализированная модель обходит универсальный Whisper с большим отрывом. На реальных
русских встречах GigaAM v3 дает чистый текст с пунктуацией на уровне платного облачного сервиса, тогда
как локальный Whisper (large-v3-turbo) гарблит слова и теряет пунктуацию. Скорость сопоставима
(~20x realtime в исторических замерах проекта на отдельных записях). Это не универсальная
оценка качества или скорости: сравнивайте движки на своем языке, оборудовании и аудио.

## Что на выходе

Markdown с шапкой и транскриптом:

```markdown
# встреча

**Файл:** встреча.mp4
**Длительность:** 17:49
**Движок:** GigaAM v3_e2e_rnnt (ASR) + sherpa-onnx/campplus (диаризация)
**Спикеров выделено:** 3 (разметка надежна на длинных репликах, короткие могут путаться - сверить вручную)

## Транскрипт

**[00:00] Спикер 1:** ...
**[00:23] Спикер 2:** ...
```

## Установка

Нужны macOS или Linux, Python 3.10+, git и `ffmpeg` в PATH.

```bash
git clone https://github.com/dewil/giga-transcribe.git
cd giga-transcribe
./install.sh          # --titanet - доп. качает более крупный (сильнее, медленнее) эмбеддинг диаризации
```

`install.sh` создает самодостаточный каталог (дефолт `~/.local/share/giga-transcribe`): venv с
GigaAM + sherpa-onnx, модели диаризации, launcher `transcribe-meeting` в `~/.local/bin` и (на macOS)
Быстрое действие Finder. При первом запуске качает несколько сотен МБ моделей.

## Использование

**Терминал**
```bash
transcribe-meeting "запись.webm" --speakers 3         # -> запись.md рядом с файлом
transcribe-meeting audio.m4a -o notes.md --title "Недельный синк"
transcribe-meeting call.mp3 --no-diar                 # чистый текст, без спикеров, быстрее
```

| флаг | смысл |
|---|---|
| `--speakers N` | число участников (точнее диаризация; без флага - авто) |
| `--no-diar` | без диаризации, чистый текст по паузам |
| `--split-channels` | один файл, каналы = спикеры (см. "Дорожки вместо диаризации") |
| `--track-names "Иван,Петр"` | имена спикеров по дорожкам |
| `--no-bleed-filter` | не убирать протечки чужого голоса между дорожками |
| `--embedding titanet` | эмбеддинг titanet (если ставил с `--titanet`) |
| `--threads N` | число CPU-потоков; по умолчанию половина доступных ядер, максимум 4; 0 = дефолт библиотек |
| `--fast` | использовать все доступные CPU-ядра |
| `-o PATH` | путь вывода (по умолчанию рядом со входом) |
| `--title` | заголовок в markdown |

**Дорожки вместо диаризации.** Если голоса уже разложены по дорожкам - пофайловым экспортом
участников или каналами внутри файла - диаризацию можно не запускать вообще: спикер известен по
построению. Разметка выходит точная, а не приблизительная, и сразу с именами; вдобавок чище работает
ASR, потому что на своей дорожке голос не перекрыт чужим.

```bash
transcribe-meeting ivan.wav petr.wav --track-names "Иван,Петр"   # дорожка = участник
transcribe-meeting call.wav --split-channels                     # каналы = участники
```

Дорожки бывают не изолированные (общий микрофон в комнате, эхо из колонок): тогда чужой голос
протекает в соседнюю дорожку тише и с искаженным текстом, и "спикер = дорожка" напечатал бы одну
реплику дважды от разных людей. Такие двойники отсекаются автоматически - по пересечению во времени
плюс одновременно похожему тексту и заметно более тихой записи. Одного пересечения мало: люди перебивают друг
друга и по-настоящему. Выключается флагом `--no-bleed-filter`.

stdout - путь к результату (удобно для пайпов); прогресс идет в stderr.

**macOS Быстрое действие** - правый клик по аудио/видео в Finder -> Службы ->
"Транскрибировать (GigaAM)". Уведомления показывают прогресс, md ложится рядом с файлом. (Руками
поставленное Быстрое действие попадает в подменю *Службы*; чтобы поднять его в секцию *Быстрые
действия*, открой бандл один раз в Automator и сохрани.)

**Как скилл для агента** - [skill/SKILL.md](skill/SKILL.md) это драйвер для кодинг-агентов (Claude Code
и т.п.): найти локальную запись, транскрибировать, положить md по конвенциям встреч проекта.

## Ограничения

- **Диаризация - свой кластеризатор.** sherpa только сегментирует речь; спикеров разводим сами
  (эмбеддинг каждого сегмента + сферический k-means). Встроенная кластеризация sherpa на длинных
  файлах вырождается (все в одного спикера либо сотни микрокластеров), поэтому заменена. С `--speakers N`
  берем k=N; без флага число оценивается автоматически (silhouette). На длинных содержательных репликах
  разметка надежна (~95% против облака), но **короткие backchannel** ("угу", быстрые вопросы) могут
  уходить не тому спикеру - в такой сегмент лезет соседний голос. Это неустранимый хвост смешанной
  записи. Облачные сервисы дают чистые N спикеров с именами, потому что берут разметку из метаданных
  платформы звонка. Спикеры тут обезличенные, имена проставляй вручную. **Если рекордер умеет
  экспортировать дорожки по участникам - подавай их** (см. "Дорожки вместо диаризации" выше):
  тогда этот раздел ограничений не про тебя, разметка становится точной и именованной.
- **Несколько проектов на одной машине.** Движок один, и параллельные прогоны надо разводить: один
  процесс держит ~1,5 ГБ и занимает ядра, а веса качаются неатомарно. Очередь через `flock`, проверка
  свободной памяти и лимит cgroup требуют проверки в установленной версии. Возможности
  своей установки смотрите через `transcribe-meeting --help`; не запускайте несколько
  тяжелых прогонов одновременно без настроенного ограничения ресурсов.
- **Инференс на CPU.** Час записи - ~10-15 мин на ноутбуке Apple Silicon. По умолчанию используется половина доступных ядер, максимум 4; флаг `--threads N` распараллеливает матричные операции (заметно быстрее на многоядерных).
  Норм для пакетной/постфактум обработки; для потока - гоняй на GPU-хосте.

### Установка и обновление из коммита

Исходники и исполняемая установка хранятся отдельно. Например:

```bash
GIGA_TRANSCRIBE_HOME=/data/apps/giga-transcribe ./install.sh
python3 deploy.py --home /data/apps/giga-transcribe \
  --launcher "$HOME/.local/bin/transcribe-meeting" --ref HEAD
```

`install.sh` предназначен только для новой установки: при существующем runtime или venv
останавливается до изменения зависимостей. Он берет файлы из коммита HEAD, устанавливает
GigaAM обычным пакетом (без editable-ссылки) и вызывает deploy. Новые зависимости пока
не закреплены lock-файлом: перед переносом окружения сравните `pip freeze` с проверенным.

`deploy.py` не устанавливает и не обновляет зависимости. Требует подготовленные
`HOME/venv/bin/python` и `HOME/models`; проверяет архив выбранного коммита против полного
`git ls-tree`, отклоняет symlink, submodule, LFS и преобразования export-ignore/export-subst.
Незакоммиченные файлы в установку не попадают. Тесты и `--help` проходят в архиве с
интерпретатором целевого venv; затем атомарно заменяются скрипт, `REVISION` (commit и SHA256)
и launcher. Для подготовки без переключения команды используйте `--no-launcher` вместо
`--launcher`. Модели, venv и общий runtime lock не изменяются.

Первая замена существующего скрипта без `REVISION` требует `--adopt-existing` после
сохранения и сверки локальных правок. После принятия SHA256 изменение установленного
скрипта блокирует обновление даже с этим флагом. Не запускайте два deploy одновременно.
Уже запущенная транскрипция продолжает работу со старым загруженным кодом.

Перед заменой deploy сохраняет прежние файлы в `HOME/deploy-backup-*`: `manifest.json`
связывает номера копий с исходными путями. При ошибке записи выполняется автоматический
откат; при аварийном завершении процесса восстановите существующие копии по manifest
(launcher должен сохранить право исполнения). Для обычного отката на старый коммит
снова запустите deploy с `--ref <commit>`: будут повторены проверки. Наличие моделей и
успешный `--help` не заменяют проверку распознавания на разрешенной тестовой записи.
