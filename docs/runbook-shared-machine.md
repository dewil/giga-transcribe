# Runbook: несколько проектов на одной машине

Что делать, когда транскрибацию с одной машины запускают из разных мест - несколько рабочих
папок, несколько кодинг-агентов, cron. Проверено на Linux x86 (4 ядра, 12 ГБ RAM, без GPU);
раздел про cgroup - только Linux, остальное общее.

Симптом, ради которого написано: два прогона стартовали одновременно, память кончилась, и
OOM-killer убил **не** транскрибацию, а то, что оказалось жирнее - базу, докер, сессию. Инструмент
при этом отработал "нормально".

## 1. Один движок на машину

`install.sh` уже ставит все в один каталог (`~/.local/share/giga-transcribe` по умолчанию) и кладет
launcher в `~/.local/bin`. Проблема не в установщике, а в том, что про эту установку **не знают
соседние проекты**: агент, работающий в другой папке, видит задачу "нужна локальная транскрипция",
не находит ничего в своем проекте и разворачивает второй экземпляр - свой venv, свой клон GigaAM,
свои копии моделей. Это несколько гигабайт впустую, но хуже другое: **вторая установка не участвует
в очереди из раздела 2** и обесценивает любую защиту.

Что помогает:

- Держать короткую справку "что уже стоит на машине и как звать" в **пользовательском**, а не
  проектном конфиге агента - для Claude Code это `~/.claude/CLAUDE.md`, он читается во всех
  проектах устройства. Достаточно таблицы путей, строчки запуска и явного "своей копии не ставить".
- Не копировать `transcribe_meeting.py` в проекты. Проектной остается только тонкая обертка под
  конвенции этого проекта (куда класть md, как назвать), вызывающая общий CLI.
- Проверить, что launcher в `~/.local/bin/transcribe-meeting` - именно от `install.sh`, а не
  перезаписан чьим-то самописным скриптом (легко случается, имя очевидное).

## 2. Очередь: один прогон за раз

Взаимное исключение нужно не из-за имен временных файлов (свой `mkdtemp` на прогон это уже
закрывает), а из-за ресурсов:

- один процесс держит **~1,5 ГБ RSS** (модель плюс torch) - замер на `v3_e2e_rnnt` после загрузки,
  до инференса;
- `--threads N` распараллеливает матричные операции, и два прогона на одной машине дерутся за одни
  и те же ядра: суммарно медленнее, чем последовательно;
- `_download_file` в gigaam пишет веса **прямо в целевой файл** и считает готовым любой
  существующий - два одновременных первых запуска с новой моделью оставляют битый кэш, который
  потом молча загружается.

Реализация - `flock` на общий файл, взятый **до тяжелых импортов**: ждущий процесс висит на голом
интерпретаторе (~20 МБ) и грузит модель, только получив лок. Поэтому очередь любой длины стоит по
памяти как один прогон.

```python
LOCK_FILE = MODELS_DIR / ".transcribe.lock"

def acquire_lock(source: Path, wait: bool, timeout: int) -> None:
    lock_fd = open(LOCK_FILE, "a+")          # "a+", а не "w": не затираем данные держателя
    try:
        fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
    except BlockingIOError:
        holder = describe_holder(read_lock_info())   # см. ниже
        if not wait:
            sys.exit(f"Занято: {holder}")
        print(f"Жду очереди: сейчас {holder}")
        deadline = time.time() + timeout
        while True:
            try:
                fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
                break
            except BlockingIOError:
                if time.time() > deadline:
                    sys.exit(f"Не дождался за {timeout // 60} мин: все еще {holder}")
                time.sleep(5)
    lock_fd.seek(0); lock_fd.truncate()
    json.dump({"pid": os.getpid(), "project": detect_project(source),
               "file": source.name, "started": datetime.now().isoformat(timespec="seconds")},
              lock_fd, ensure_ascii=False)
    lock_fd.flush()                          # держим fd открытым до конца процесса
```

Две детали, без которых очередь раздражает:

**Писать в лок, кто занял.** Не только pid, а проект, файл и время старта. Разница для человека:

```
Занято: на машине уже идет транскрибация - проект "клиент-А", файл 2026-07-27.webm,
идет 6 мин (с 22:31), pid 1746675.
```

против безликого "ресурс занят". Заодно видно, какой pid снимать, если прогон завис. Имя проекта
дешево получить, поднимаясь от обрабатываемого файла вверх до маркера рабочей папки:

```python
def detect_project(path: Path) -> str:
    for parent in [path.resolve(), *path.resolve().parents]:
        for marker in ("CLAUDE.md", ".claude", ".git"):
            if (parent / marker).exists():
                return parent.name
    return Path.cwd().name
```

**Ограничивать ожидание** (`--wait-timeout`, разумный дефолт - пара часов). Иначе один зависший
держатель подвешивает всех остальных навсегда, и это выглядит как "инструмент сломался".

Лок снимает ядро при завершении процесса, в том числе аварийном, - отдельная уборка не нужна.

## 3. Проверка памяти до старта

Лок бывает свободен, а память - уже нет: браузер, агенты, база. Дешевле подождать, чем поймать OOM.

```python
def mem_available_mb() -> int:
    for line in Path("/proc/meminfo").read_text().splitlines():
        if line.startswith("MemAvailable:"):
            return int(line.split()[1]) // 1024
    return 0
```

Порог берем с запасом над рабочим набором (~1,5 ГБ): 2,5 ГБ - разумный дефолт. Поведение то же, что
у очереди: ждем до таймаута, с `--no-wait` выходим сразу и печатаем, сколько сейчас свободно.

## 4. Лимит памяти через cgroup (Linux)

Главный пункт против "положил машину". Без лимита превышение обрабатывает **глобальный**
OOM-killer, и жертву выбирает он - по своему счету, а не по вине. С лимитом OOM срабатывает
**внутри cgroup**: худший исход - умерла транскрибация, машина цела.

Прогон перезапускает себя внутри scope, если он там еще не находится:

```python
def reexec_in_scope(memory_max: str) -> None:
    if os.environ.get("TRANSCRIBE_SCOPE") or not shutil.which("systemd-run"):
        return
    cmd = ["systemd-run", "--user", "--scope", "--quiet",
           "-p", f"MemoryMax={memory_max}", "-p", "MemorySwapMax=0",
           "--", os.path.abspath(sys.argv[0]), *sys.argv[1:]]
    os.execvpe(cmd[0], cmd, dict(os.environ, TRANSCRIBE_SCOPE="1"))
```

- `MemoryMax=4G` - запас над рабочим набором; при упоре процесс молча получает "Killed", лечится
  повышением лимита.
- `MemorySwapMax=0` - без этого инференс уходит в своп и машина встает по отзывчивости не хуже, чем
  при нехватке памяти.
- Флаг отключения (`--no-limit`) и мягкая деградация обязательны: на системах без systemd-user
  (контейнер, WSL без systemd, не-Linux) нужно предупредить и работать без лимита, а не падать.

Проверка, что лимит реально применился, на работающем прогоне:

```bash
cg=$(cut -d: -f3 /proc/<pid>/cgroup)
cat /sys/fs/cgroup$cg/memory.max        # 4294967296 при MemoryMax=4G
cat /sys/fs/cgroup$cg/memory.swap.max   # 0
```

## 5. Что дает Linux-машина по числам

Замеры на 4 ядрах x86 без GPU, модель `v3_e2e_rnnt`, `--threads 4`:

| Что | Значение |
| --- | --- |
| RSS одного процесса после загрузки модели | ~1,5 ГБ |
| RTF (доля реального времени) | ≈ 0,2 |
| 42-минутная запись целиком | ~15 мин, из них диаризация - секунды |
| Разумный `MemoryMax` | 4G |

Для сравнения с Apple Silicon - `benchmarks.md`; там числа получены на другом железе, и разница по
скорости в разы, а не в процентах.

## 6. Установка на Linux без root

`install.sh` предупреждает про отсутствие ffmpeg и предлагает `apt install` - на машине без sudo это
тупик. Рабочий обход - статический бинарник в тот же `~/.local/bin`:

```bash
cd /tmp
curl -sLO https://johnvansickle.com/ffmpeg/releases/ffmpeg-release-amd64-static.tar.xz
tar xf ffmpeg-release-amd64-static.tar.xz
cp ffmpeg-*-static/ffmpeg ffmpeg-*-static/ffprobe ~/.local/bin/
```

Остальное (venv, GigaAM с extras `[torch]`, sherpa-onnx, модели) ставится в домашнюю папку и root не
требует.

## 7. Диагностика

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Процесс молча "Killed" | упор в `MemoryMax` cgroup | поднять `--memory-max`, проверить `memory.max` |
| Все прогоны висят в ожидании | зависший держатель лока | взять pid из сообщения/файла лока, снять |
| Битые веса, странные ошибки загрузки модели | одновременное первое скачивание в два процесса | удалить кэш модели, перекачать одним прогоном |
| Машина встает при одном прогоне | инференс ушел в своп | `MemorySwapMax=0`, поднять порог свободной памяти |
| Второй экземпляр движка в системе | сосед поставил свою копию | снести, оставить один, вписать справку в конфиг агента |
